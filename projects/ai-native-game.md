## 为什么做
业界现在越来越追求两件事：**一口气生成一个能玩的游戏**，以及**自动化调试**。这两件事把瓶颈压在同一处：agent 能不能高效、可靠地读写引擎资源，并且知道自己改得对不对。

## 我读了什么
2026-11-01 读了三个开源项目的文档和代码（只读，没有运行它们），它们各自回答了这条流程里的一环。

**[Autopilot](https://github.com/ramenvr/autopilot)：自动试玩与验证**（Apache-2.0）
- 给 agent 的是一套 harness 工具包：可以特权读取任意对象的属性、调用蓝图函数、读取“玩家能看到什么”、列出并操作界面；但**行动只能通过“玩家的手”**（按键、鼠标）。直接写状态的操作被明确标成“不是玩家行为”，并单独上报。
- “完成”的判据读**游戏自己的状态**（比如背包里有钥匙、门是开的），而不是 agent 自己说完成了。
- 评测用一组带期望裁决（确认、否定、达成）的提示；游戏以无渲染的无头方式运行；并对比“冷启动”和“带记忆”两种情况。
- 项目记忆分开存放：已验证的事实、可复用的代码、每次运行的轨迹和报告。

**[VibeGame](https://github.com/tettethu/VibeGame)：提示到游戏的多智能体**（Apache-2.0，附技术报告）
- 项目状态用结构化文本表示，带显式引用和校验，agent 才能安全地读写。
- 运行时帧同步可控：agent 可以暂停、步进、注入输入，再观察结果。
- 对抗式智能体团队：把“实现”和“评测”分开，审计、试玩、评审发现的失败会变成修复任务，重新进入开发。
- 经验沉淀：把通过验收的项目整理成对应某类游戏的可运行项目模板、已验证的模块和协作契约，下次改编后**重新验证**，而不是直接照搬。

**[video-to-game](https://github.com/lovisdotio/video-to-game)：视频到游戏**（MIT）
- 游戏对外暴露一份**只读的状态**（玩家在屏幕上能看到的数字）；试玩脚本只读它、只用键盘，**从不写入、不传送**。
- 录制按真实帧率，挑出最精彩的片段，并把视频与游戏在同样位置并排对比。
- 有完整的成本账（调用次数和费用）。

三个项目的共同点：**让 agent 读到可靠的状态，用玩家式的输入去操作，用游戏自己的状态去判定对错。**

## 我打算怎么搭（在 UE 里）
先把范围收窄到一个小而完整的玩法原型（比如一个小关卡），再按下面的环节搭：

1. **生成**：agent 根据需求生成玩法原型。
2. **资源读写**：agent 通过引擎接口读写资源（材质、关卡、依赖关系），目标是 token 少、可批量、可校验。
3. **状态契约**：在 UE 里导出一份只读的游戏状态；agent 只通过玩家式输入去操作，直接改状态的操作单独标记并上报。
4. **自动验证**：“完成”由读游戏状态的判据决定；证据（日志、截图、轨迹）落盘，能复查。
5. **自动调试**：验证失败时，复现问题、定位到具体的资源或 Shader，修复后再次验证。
6. **批量处理**：成批、重复的检查和分诊（截图、日志、资产），先由低价模型粗筛，难的再交给更强的模型。

有一点我会特别关注：Autopilot 的无头运行**不渲染**，所以画面和 GPU 耗时相关的验证，需要另一条有渲染的路径。这正是我的渲染和性能分析背景能补上的一块。

## 评测设计
沿用我做神经材质基准时的思路：固定任务、固定环境、可复现、有基线。

- **任务集**：每条任务带期望结果（对应 Autopilot 的“确认、否定、达成”），先从小而明确的验证题开始。
- **指标**：一次成功率、需要人工介入的次数、token 与耗时、成本。
- **对比**：冷启动对比带记忆；低价模型对比强模型的准确率和每千个任务的成本。

## 阶段目标
每一阶段都以可度量的完成标准为准。

- **阶段 0**：任务集与评测框架（可复现、有基线）。
- **阶段 1**：UE 里的只读状态契约，加上玩家式输入注入（最小版本）。
- **阶段 2**：自动验证闭环——判据读游戏状态，证据落盘。
- **阶段 3**：失败后自动复现、定位、修复，再验证。
- **阶段 4**：批量分诊，以及经验的沉淀与复用。
